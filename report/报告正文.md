## 2　关键实现

全部实现集中在 `image_encoder.py` 的六处 TODO，其余提供文件未作修改。

### 2.1　patchify 的形状变化

输入 `[B,3,224,224]` 在内存中以 C 轴最外、像素先行后列的方式连续存放。实现分三步：

1. **拆分两套轴**：`reshape(B, 3, 7, 32, 7, 32)`，把「属于哪一块」（网格行/列）和「块内哪一点」（patch 内行/列）分离；
2. **重排优先级**：`transpose(0, 2, 4, 1, 3, 5)` 得到 `[B,7,7,3,32,32]`，令 patch 索引（先行后列）排在最前，块内按 C,H,W 排在其后；
3. **拍平**：`reshape(B, 49, 3072)`，前 49 个位置即行优先的 patch 序号，后 3072 = 3×32×32 为该 patch 的 RGB 展开值。

这与 `visual.conv1.weight` 的 32×32×3 卷积核完全等价，因此 patch 投影可直接写成 `patches @ W.T` 且**没有偏置项**。需要注意，若跳过第 1 步直接 reshape，网格行与块内行会混在同一轴上，虽然最终形状相同，但数值顺序错误——`check.py --stage patches` 会立刻暴露这一点。

### 2.2　多头注意力

QKV 由一次线性投影得到后按 `width` 切分，再拆成 12 个头。两个容易出错的实现决定：

- **拆头顺序**：必须先 `reshape(B, N, 12, 64)` 再 `transpose(0, 2, 1, 3)` 得到 `[B,12,N,64]`。若直接 reshape 成 `[B,12,N,64]`，不同 token 的特征会被交错分配到同一头，token 顺序被破坏。
- **4 维 k 的转置**：真实 k 是 `[B,12,N,64]`，打分时只交换最后两维 `k.swapaxes(-1,-2)`，得到 `[B,12,N,N]`；教学用的 `transformer_steps.py` 里 k 是二维表，用 `k.T` 即可，两者不能照搬。

完整计算为 `scores = q·kᵀ/√64 → softmax → coefficients @ v → 合并头 → 输出投影`。合并头时用 `transpose(0,2,1,3).reshape(B,N,768)`，与拆头互为逆操作。

### 2.3　残差、MLP 与输出头

单个 Block 含两次残差相加，且不含 LayerScale：

```
residual  = x + Attention(norm1(x))
u         = norm2(residual)
mlp       = GELU(u @ W1.T + b1) @ W2.T + b2
output    = residual + mlp
```

其中 GELU 使用课程提供的 erf 精确版，LayerNorm 的 eps 固定为 1e-5。输出头取 `tokens[:, 0:1, :]`（保留三维以复用 LayerNorm），经 `post_norm` 后与 `visual.proj` 相乘，最后调用 `unit_vector` 缩放为单位长度。

### 2.4　权重布局与精度约定（贯穿全文件）

课程提供的线性层权重均按 `[out,in]` 存放，因此统一写作 `x @ W.T + b`；**唯一例外**是 `visual.proj` 已经是 `[in,out]=[768,512]`，直接相乘、不可转置。此外 patch 投影无 bias，全程保持 float32，`check.py` 会对返回值断言 dtype 与有限性。

## 3　数值验收

在 `project1-numpy-student/` 下执行 `python check.py --stage all`，8 个阶段全部通过。各阶段与独立 FP32 参考的最大/平均绝对误差如下：

| 阶段 | 形状 | max_abs | mean_abs | 容差 (atol, rtol) |
|---|---|---|---|---|
| preprocess | (10, 3, 224, 224) | 0.000e+00 | 0.000e+00 | 2e-6, 2e-4 |
| patches | (2, 49, 3072) | 0.000e+00 | 0.000e+00 | 2e-4, 2e-4 |
| tokens | (2, 50, 768) | 4.005e-05 | 1.289e-06 | 2e-4, 2e-4 |
| block0 | (2, 50, 768) | 7.063e-06 | 3.250e-07 | 2e-4, 2e-4 |
| last_tokens | (2, 50, 768) | 4.768e-05 | 2.696e-06 | 2e-4, 2e-4 |
| output | (10, 512) | 5.439e-07 | 8.311e-08 | 2e-5, 2e-4 |
| batch | (3, 512) | 4.619e-07 | 7.632e-08 | 2e-5, 2e-4 |

误差均在 1e-5 量级以下，远小于容差；输出向量的单位长度最大偏差约 1.2e-07，处于 float32 精度极限。`batch` 阶段会打乱图片顺序并重复取样，通过它说明实现确实按 batch 计算，而非缓存参考结果。

额外做了两项验证：

- `python run.py --output output_tokens.npz` 生成 10 张图的结果，`(10, 512)` float32，全部有限；
- 用一张**未包含在参考集中的图片**（课堂示例 `uw_cat.png`）执行 `python run.py --images ... --output ...`，得到 `(1, 512)` float32、有限且单位长度偏差为 0，证明实现对新输入同样成立。

## 4　设计阶段识别的数值陷阱（之一，附反例验证）

本次实现为首跑通过，没有发生需要返工的调试。但课程要求说明一个「bug」，因此如实记录一个**在编写时识别、并用反例实验确认**的典型陷阱，而非虚构调试过程。

**问题**：注意力打分需除以 √64。若写成 `scores = q @ k.swapaxes(-1,-2) / np.sqrt(64)`，`np.sqrt(64)` 返回的是 NumPy 的 `float64` 标量（不是 Python float）。在 NumPy 2 的类型提升规则（NEP 50）下，NumPy 标量属于强类型，`float32` 数组与之相除会被整体提升为 **float64**，违反「全程 float32」契约，`check.py` 的 dtype 断言会直接判失败。

**实测证据**（NumPy 2.5.4）：

```
np.sqrt(64)                    -> float64
s / np.sqrt(64)               -> dtype = float64   ← 陷阱
s / np.sqrt(np.float32(64))   -> dtype = float32   ← 采用
```

**规避**：代码中使用 `np.sqrt(np.float32(self.head_dim))`，把缩放因子约束为 float32 标量。等价写法也可以在乘法前先 `scores.astype(np.float32)`，但显式约束标量类型更贴近意图。

同一阶段还主动规避了另外两个常见错误：拆头时先 `[B,N,12,64]` 再转置（见 2.2）；以及 `visual.proj` 是全文件唯一不转置的权重（见 2.4）。
